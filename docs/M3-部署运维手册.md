# M3 联邦学习 部署运维手册

> 版本：v1.0 · 日期：2026-08-01 · 前置：[M2 部署运维手册](./M2-部署运维手册.md)
> 版本锁定：**FATE 1.11.3 + FATE-Serving 2.1.6**（选型依据见 [S0 报告](./M3-S0版本PoC报告.md)）

## 1. 组件与端口

| 组件 | 镜像 | 端口 | 作用 |
|---|---|---|---|
| FATE standalone | `federatedai/standalone_fate:1.11.3` | 9380（Flow REST）、8080（FATEBoard） | 训练引擎（开发态单容器含 guest 9999 / host 10000） |
| ZooKeeper | `zookeeper:3.8` | 2181 | Serving 组件注册中心 |
| serving-server | `federatedai/serving-server:2.1.6-release` | 8000 | 模型加载与推理执行 |
| serving-proxy | `federatedai/serving-proxy:2.1.6-release` | 8059（HTTP 推理）、8869（跨方 gRPC） | 推理入口与联邦路由 |
| 平台节点 | 本工程 | 18001（控制面 mTLS）、17001（管理面） | 治理面（M2） |

**镜像均为 amd64**：Apple Silicon 经 Rosetta 仿真，仅作开发环境；生产用 x86。

## 2. 启动顺序

```bash
# 1. FATE 训练侧（含 Flow 0.0.0.0 绑定修正与就绪等待）
./deploy/fate/start-standalone.sh fate-s0 8080 9380
```

```bash
# 2. Serving 侧三组件
docker compose -f deploy/fate/docker-compose-serving.yml up -d
```

```bash
# 3. 接线：FATE Flow 指向 serving-proxy（容器 IP 或 compose 服务名）
PROXY_IP=$(docker inspect ppc-serving-proxy --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}')
docker exec fate-s0 bash -c "sed -i \"s|    - 127.0.0.1:8000|    - $PROXY_IP:8059|\" /data/projects/fate/conf/service_conf.yaml"
docker exec fate-s0 bash -lc "source /data/projects/fate/bin/init_env.sh && cd /data/projects/fate/fateflow && bash bin/service.sh restart"
```

```bash
# 4. 验证训练链路（官方样例，约 3 分钟）
./deploy/fate/run-hetero-lr.sh fate-s0
```

## 3. 平台侧接入

- 训练：`FedTrainingOrchestrator.run(taskId, TrainingSpec)`——数据须先经 connector 指纹复核后
  `FateFlowClient.uploadServerLocal` 灌入本方 Flow（**数据经共享卷交付本方容器，不出本方**）；
- 出库：`ModelReleaseService.confirmReleaseApproved` → `export`（粒度与审批双闸门）；
- 推理：`ScoringClient(proxyBaseUrl, serviceId).score(subjectId, localFeatures)`。

Java 侧配置示例：

```java
var fate = new FateFlowClient("http://localhost:9380");
var orchestrator = new FedTrainingOrchestrator(tasks, audit, fate, registry, "A", 15 * 60_000);
var scoring = new ScoringClient("http://localhost:8059", "risk-model");
```

## 3.1 模型发布（deploy → load → bind → 自检）

```bash
./deploy/fate/publish-model.sh <训练jobId> [serviceId]
```

脚本封装了三个必踩的坑（详见验收报告 B1）：① 必须先 `model deploy` 再对**新版本号** load；
② `servings` 必须指向 **serving-server:8000**（gRPC ModelService），指 proxy 的任何端口都不行；
③ `fateflow.host` 必须是容器真实 IP（0.0.0.0 会写进 transfer URL 导致 Serving 拉不到模型）。

## 4. 运维要点

- **模型下发**：用 §3.1 脚本；手工排查时按「deploy 了吗 → servings 指对了吗 → transfer URL 可路由吗」三步走；
- **数据卷**：训练数据须在 FATE 容器可见路径（`use_local_data=0` 语义），
  生产以只读卷挂载本方数据目录，禁止跨方共享卷；
- **日志**：Flow `/data/projects/fate/fateflow/logs/{job_id}/`；Serving `docker logs`；
  FATEBoard http://localhost:8080 看任务 DAG 与指标曲线；
- **清理**：`flow data delete`（表）、`flow job stop`（任务）；容器停用 `docker rm -f`。

## 5. 已知边界

1. `flow model load` 未通（验收报告 B1）——在线推理链路最后一环待定位；
2. 单容器 standalone 拓扑：跨方真实集群互联（rollsite/osx + 证书）需双机环境验证；
3. 性能数据为仿真环境，SLA 须 x86 复测；
4. FATE 容器属**受控区**：容器内可直接取模型文件，模型出库治理在平台层——
   运维须以文件权限与访问审计约束容器登录（技术强制留 M4：模型加密存储）。
