## 1. 方法论与诚实边界

**软件整形模拟**（`ShapedRelay`，用户态等价 `tc netem delay+rate`）：
协议流经 loopback 中继，注入**单向 10ms 时延（RTT 20ms）+ 50Mbps 带宽上限**——
与原计划的 netem 口径（`delay 20ms rate 50mbit`，RTT 语义按单向 10ms 对齐）一致。
整形模型：块投递时刻 = 首块到达 + 时延 + 累计字节×8/速率（同时刻画传播时延与序列化时延）。

**边界声明**：

- 单机运行：双引擎共享 CPU（真机各自独占，计算段会更快）；未经过物理网卡/交换机；
- macOS 无 netem，本报告为软件整形口径；**真机矩阵**（两台 ≥8 核/32GB + 千兆直连 +
  Linux netem）的执行口径见 §4，数据到位后本报告升 v2；
- 纪律：S 档 5 次、M 档 3 次取中位数（M 档偏离 5 次纪律，原因：单机串行耗时控制）；
  每次运行交集基数与构造真值比对；
- 引擎按真实运维顺序启动（server 先行 500ms），耗时为 client 侧协议在线耗时
  （不含 JVM 启动，取自引擎自报的 done 行）。

环境同 M1 基准报告（Apple M4 / 32GB / JDK 17.0.15 / mpc4j ea3b9aa 纯 Java）。

## 3. 结论

1. **SLA 在 WAN 口径下达标（遗留项清偿的核心问题）**：PSI 100万×100万 在 RTT 20ms + 50Mbps
   下 RR22 中位 **9.5 秒**，距 SLA（≤60s）余量 6 倍以上；KKRT16 21 秒亦远内达标；
2. **通信量决定 WAN 敏感度**：RR22 的 50MB 与计算充分重叠，WAN 惩罚仅 +3%；
   KKRT16 的 150MB 受 50Mbps 序列化时延主导，惩罚 +34%——**带宽受限链路上 RR22 优势进一步扩大**；
3. **对千万级选型的推论**（待真机实测确认）：KKRT16 L 档通信 1.36GB @50Mbps 仅传输即 ≈218s，
   低带宽链路上「RR22 分批」（约 4 批 × ~50MB 量级）可能反超 KKRT16，选型器应把**链路带宽**
   纳入决策维度（M3 backlog）；
4. S 档差异在噪声区间内（RTT 20ms 对亚秒级任务的往返次数不构成主导项）。

## 4. 真机矩阵执行口径（数据到位后本报告升 v2）

1. 机器：2 ×（≥8 核 / 32GB），千兆交换机直连；`iperf3` 带宽与 `ping` RTT 基线入环境指纹；
2. WAN 模拟在 B 侧 Linux：`tc qdisc add dev <网卡> root netem delay 20ms rate 50mbit`，测毕删除；
3. 双方各自运行：`NetworkMatrixBench` 的双机版即 `NettyPsiPartyMain`（改 yaml 端点）+
   S0 报告的记录口径；每组 5 次取中位数；
4. L 档（千万级）补测 KKRT16（`-Xmx26g`）与 RR22 分批；
5. 数据回填本报告 §2 并升版，SLA（M2 §4.9）随之定稿。
