## 1. 定位与目标

### 1.1 业务问题

前三个里程碑解决的是「**双方都想算、但都不想给数据**」（PSI/联合统计/联邦建模）。
PIR 解决的是另一类刚需：「**查询方想查，但连查了谁都不想让对方知道**」。

典型场景：

- 银行向征信机构查某人的信用记录——征信方**不应知道**银行在查谁（否则泄露银行的授信意向）；
- 反诈系统查某号码是否在黑名单——查询行为本身即敏感；
- 医保向药企查某药品信息——查询模式暴露采购计划。

PSI 求的是「双方交集」，PIR 求的是「**我要的那一条，你不知道是哪条**」——语义完全不同，
不能相互替代。

### 1.2 目标

**把匿踪查询作为新任务类型纳入既有治理框架**：契约协商 → 引擎执行 → 查询配额治理 → 审计留痕。

### 1.3 验收标准

1. 关键字匿踪查询（KS-PIR）双节点端到端：查询方拿到正确 value，**数据方无从得知查了哪个 key**；
2. 查询命中与未命中语义正确（未命中不泄露"存在与否"之外的信息）；
3. **查询配额治理**：PIR 的隐私风险随查询次数累积（查得足够多等于拖库），
   平台按数据集记账查询次数并熔断——语义对齐 DP 预算中心；
4. 全链路审计：契约、查询批次、配额消耗、结果规模（不记录查询内容本身）；
5. 性能基准：10 万 / 100 万条库的初始化与在线查询耗时。

### 1.4 明确不做

- 依赖 `mpc4j-native-fhe` 的 PIR 实现（Label PSI 系、stdpir/index 的 SEAL 系）——见 §2 选型；
- 多方 PIR、可验证 PIR；
- 查询内容的语义级审计（与匿踪目标直接冲突，见 §4.3）。

## 2. 技术选型（调研已完成）

mpc4j 的 PIR 实现分两大族，**native 依赖是决定性因素**：

| 族 | 实现 | native 依赖 | 结论 |
|---|---|---|---|
| `stdpir/index`（标准索引 PIR） | XPIR/SealPIR/OnionPIR/FastPIR… | **21 个文件依赖 SEAL** | 排除（引 C++ 工具链违背 M1 的 C5 约束） |
| `stdpir/ks`（Label PSI 系关键字 PIR） | Label_PSI | **依赖 mpc4j-native-fhe** | 排除（同上） |
| **`cppir/ks`（客户端预处理关键字 PIR）** | PAI_CKS、ALPR21、CHALAMET、SIMPLE_NAIVE/BIN/PGM | **零 native，纯 Java** | **选定** |
| `cppir/index` | frodo/mir/pai/piano/plinko/simple | 零 native | 备选（按索引查，业务语义弱于关键字） |

**选定 `cppir/ks`（CpKsPir）**，与 M1 确立的「默认纯 Java 路径（C5）」一脉相承。
一期协议取 **PAI_CKS**（论文实现完整）与 **SIMPLE_NAIVE**（对照组），运行期可切换。

**客户端预处理 PIR 的代价与收益**（诚实边界）：
客户端首次需下载/预处理一份与库规模相关的提示（hint），换取**在线查询的极低通信量**；
即库越大初始化越贵、但单次查询越便宜。适合「一次建库、高频查询」场景——正是匿踪查询的常态。
初始化成本进基准（§5 验收标准 5）。

### 2.1 API 契约（已核实）

```java
// 数据方（server）：持库
CpKsPirServer<T> server = CpKsPirFactory.createServer(rpc, clientParty, config);
server.init(Map<T, byte[]> keyValueMap, int l, int maxBatchNum);   // l = value 字节长
server.pir(int batchNum);                                          // 应答一批查询

// 查询方（client）：只知道库规模 n 与 value 长度 l
CpKsPirClient<T> client = CpKsPirFactory.createClient(rpc, serverParty, config);
client.init(int n, int l, int maxBatchNum);
byte[][] values = client.pir(ArrayList<T> keys);                   // 批量查询
```

## 3. 架构设计（最大化复用）

PIR 与 PSI 同为「两方协议 + 独立引擎进程」，**复用 M2 建立的全部基础设施**：

| 复用资产 | 用法 |
|---|---|
| `ppc-engine-psi` 进程模型 | 扩展为通用协议引擎：job 文件新增 `protocolFamily=psi\|pir`，同一进程按族分派 |
| `NettyPsiRunner` 的 RPC 构造 | PIR 复用同一 netty 对等连接与端点约定 |
| 协议面 TLS 隧道（M2.5 #1） | 原样复用（隧道在传输层，与协议族无关） |
| 契约/状态机/协商/审计 | 新增 `TaskType.PIR_QUERY`，流程不变 |
| `BudgetCenter` | 语义平移为**查询配额**（见 §4.2） |

**不新建模块**：PIR 引擎代码进 `ppc-psi`（更名语义上略勉强，但避免为一个协议族新增 Maven 模块——
模块边界按「JDK/preview 约束」划分而非按协议划分，这是 M2 ADR-1 的既定原则）。

## 4. 关键设计

### 4.1 任务模型

契约新增字段（沿用既有 `TaskContract`，不破坏兼容）：

```
taskType   = PIR_QUERY
protocol   = pai_cks | simple_naive          # 复用 protocol 字段
datasetLocal / datasetPeer                    # 数据方的库 / 查询方的查询集来源
outputGranularity = INTERSECTION_DETAIL       # 查询方获得 value 明细（语义即"查询结果"）
```

角色约定：**发起方 = 查询方（client）**，**响应方 = 数据方（server）**——
与 PSI 任务的角色分配相反（PSI 里发起方通常是出题方/server），故引擎 job 显式带 role。

### 4.2 查询配额治理（M4 的治理增量）

**问题**：PIR 保护单次查询的隐私，但**不限制查询次数**——查询方反复查即可拖走整库。
这是 PIR 的固有风险，必须在平台层治理。

**设计**：`BudgetCenter` 的账户语义扩展为「资源配额」，PIR 用**查询条数**计量：

- 账户：`(dataset_id, total=允许查询总条数, spent=已查条数)`；
- 扣减时机：**查询前预扣**（与 DP 的「先扣后噪」同构：失败不扣、超限熔断）；
- 与 DP 预算共用一套表与并发控制（行锁事务），仅计量单位不同——
  在 `budget_account` 语义上，ε 与查询条数都是「不可再生的隐私资源」。

**诚实边界**：查询条数与真实隐私泄露量之间**没有 ε 那样的数学等价**，
配额是运营手段而非密码学保证——此点写入验收报告与手册（对齐 M3 §4.6 对联邦预算的处理）。

### 4.3 审计的边界（与匿踪目标的张力）

**绝不记录查询内容**：审计记录「谁、何时、查了几条、消耗多少配额、命中几条」，
**不记录查了哪些 key**——否则平台审计日志本身成为泄露面，与 PIR 的目的直接矛盾。

这是本里程碑一条**主动的设计克制**：审计的完备性在此处让位于隐私目标，
并在手册中明示「PIR 任务的可审计粒度低于其他任务类型」。

### 4.4 数据接入

数据方的键值库经 connector 接入：CSV `key,value` 两列 → `Map<String, byte[]>`；
沿用指纹复核（防审批后换库）。value 定长 `l` 由契约声明，短则右补零、超长即拒（协议要求定长）。

## 5. 实施计划（单 Sprint，4 个检查点）

| # | 内容 | 门禁 |
|---|---|---|
| **P1** | `CpKsPirRunner`（内存 RPC + netty 双进程）、协议选型、正确性（命中/未命中/批量） | 单测：查询结果与真值一致 |
| **P2** | 引擎进程扩展（`protocolFamily` 分派）、PIR 任务编排、契约与协商 | 双节点端到端（双引擎进程） |
| **P3** | 查询配额治理（预扣/熔断/审计）、数据接入与指纹 | 配额耗尽熔断实测；审计不含 key 的断言 |
| **P4** | 基准（10万/100万库的 init 与在线查询）、《M4 验收报告》、手册增补 | 全量回归 + 基准数据落档 |

**风险**：`cppir/ks` 各实现的参数约束（库规模、value 长度上限）未知——P1 首要验证，
不满足则切换协议或调整档位，如实记录（对齐既往「以实测定档」的做法）。

---

## 6. 与既有里程碑的关系

M4 不改动 M1-M3 的任何既有行为：新增任务类型、新增引擎协议族分派、
配额治理复用预算表——**全部为增量**。回归门禁保证既有 66 项测试不受影响。
