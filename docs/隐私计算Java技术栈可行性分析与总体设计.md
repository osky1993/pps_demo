# 隐私计算平台 Java 技术栈实现方案 —— 可行性分析与总体设计

> 版本：v0.1（草案）
> 日期：2026-08-01
> 范围：MPC（多方安全计算）、HE（同态加密）、FL（联邦学习）、DP（差分隐私）四条技术路线，暂不含 TEE（可信执行环境）

---

## 1. 背景与目标

### 1.1 背景

隐私计算的目标是让数据"可用不可见"：在不交换原始明文数据的前提下，完成多方之间的联合计算、联合建模与结果发布。四条技术路线各自覆盖数据生命周期的不同环节：

```
数据求交/对齐 ──→ 联合训练/计算 ──→ 计算外包保护 ──→ 结果发布
     MPC(PSI)        FL / MPC           HE              DP
```

本方案论证在 **Java 技术栈为主** 的前提下，四条路线的工程可行性，并给出总体设计。

### 1.2 为什么坚持 Java 技术栈

- 团队现有工程能力、CI/CD、运维监控体系均围绕 JVM 生态建设；
- 隐私计算节点通常部署在金融、政务等机构内网，这些机构的准入清单对 Java/Spring 生态接受度最高；
- JVM 的跨平台性降低多参与方异构环境（x86/ARM、不同 Linux 发行版）的交付成本；
- 长生命周期服务（网关、调度、审计）Java 的可维护性优势明显。

### 1.3 需要预先承认的约束

隐私计算开源生态的主流语言是 **Python（联邦学习）与 C++（密码学库）**，Java 是少数派。因此本方案的基本策略是：

> **"Java 原生优先，JNI 封装次之，混合栈兜底"** —— 能用 Java 原生库的路线用原生库；只有 C++ 生产级实现的（全同态加密），用 JNI/独立服务封装；生态被 Python 垄断的环节（联邦训练核心），接受混合栈并把 Java 的边界划在平台层与推理层。

## 2. 分路线可行性分析

### 2.0 结论速览

| 路线 | Java 可行性 | 推荐基线 | 实现策略 |
|---|---|---|---|
| MPC | ★★★★★ 高 | mpc4j（阿里）、FRESCO | Java 原生 |
| HE（半同态） | ★★★★☆ 高 | javallier（Paillier） | Java 原生 |
| HE（全同态） | ★★☆☆☆ 受限 | SEAL / OpenFHE | JNI 封装或 sidecar 服务 |
| FL | ★★★☆☆ 中 | FATE（训练）+ FATE-Serving（推理，纯 Java） | 混合栈，Java 管平台与推理 |
| DP | ★★★★★ 高 | Google differential-privacy（官方 Java 实现） | Java 原生 |

### 2.1 MPC：Java 原生可行，成熟度最高

**目标场景**：隐私求交（PSI）、联合统计（求和/均值/计数）、隐匿查询（PIR）。参与方明确（2~3 方），要求精确结果。

**候选开源方案**：

| 项目 | 语言 | 协议覆盖 | 评估 |
|---|---|---|---|
| **mpc4j**（alibaba-edu/mpc4j） | Java | PSI、PIR、秘密分享、OT、面向电路的通用 MPC | 目前最完整的 Java MPC 库，有顶会论文背书，工程结构规范（Maven 多模块），**首选** |
| **FRESCO**（aicis/fresco） | Java | SPDZ、TinyTables 等通用协议框架 | 抽象层设计好，适合嵌入自研应用做通用安全计算；社区活跃度一般 |
| MP-SPDZ | C++ | 学术事实标准，协议最全 | 仅作协议正确性对照与性能基准，不进入生产链路 |

**可行性论证**：

- *技术可行性*：PSI/联合统计是落地最多的 MPC 场景，mpc4j 对这两类开箱即用；通用电路计算可由 FRESCO 补位。无需跨语言调用。
- *性能*：MPC 的瓶颈在**网络通信量**（OT 扩展、秘密分享交互轮次），不在 JVM 计算性能。千万级 ID 求交在局域网/专线环境下为分钟级，Java 与 C++ 实现差距通常在可接受的常数倍以内，且可通过批处理与并行摊薄。
- *风险*：mpc4j 定位偏研究型库，API 稳定性与向后兼容需要版本锁定策略；需自建协议层的会话管理、断点重试与审计。

**结论：完全可行，Java 原生实现，无需妥协。**

### 2.2 HE：半同态 Java 原生可行；全同态需 JNI 封装

**目标场景**：不信任算力方的密文外包计算；以及作为 MPC/FL 的内部零件（如纵向联邦中的梯度加密聚合）。

**关键分野——按需求切成两档**：

**（a）半同态（PHE，密文加法即可）——覆盖绝大多数联合统计与联邦聚合场景**

| 项目 | 语言 | 评估 |
|---|---|---|
| **javallier**（n1analytics/javallier） | Java | Paillier 加法同态，API 简洁，可直接作为 Maven 依赖引入，**首选** |
| 自研 Paillier（基于 `BigInteger`） | Java | 协议简单、可控性强，作为 javallier 停止维护时的备份路径 |

*可行性*：Paillier 的数学基础只依赖大整数模幂运算，`java.math.BigInteger` 原生支持，性能瓶颈可用密文打包（packing）与批处理缓解。**Java 原生完全可行。**

**（b）全同态（FHE，需要密文乘法/任意电路）——仅在密文机器学习推理等高级场景需要**

| 项目 | 语言 | Java 接入方式 | 评估 |
|---|---|---|---|
| Microsoft SEAL | C++ | JNI 封装（社区 binding 质量参差）或 gRPC sidecar | BFV/CKKS 主流实现 |
| OpenFHE | C++ | 同上 | 协议最全，学术界推荐 |

*可行性*：**纯 Java 的生产级 FHE 实现不存在**，这是硬约束。两条务实路径：

1. **JNI 封装**：性能最好，但需维护跨平台 native 构建（Linux x86/ARM），并处理 JVM 与 native 内存边界（密钥/密文的生命周期管理）；
2. **Sidecar 服务**（推荐起步方案）：将 SEAL/OpenFHE 包成独立 C++ gRPC 服务，Java 侧只做编排。牺牲一次序列化开销，换取构建链路解耦与故障隔离。

*建议*：一期只承诺 PHE 能力（覆盖 80% 以上实际需求），FHE 以 sidecar 形式作为二期可选增强，不让 FHE 阻塞整体交付。

**结论：半同态原生可行；全同态受限，用 sidecar 策略控制风险。**

### 2.3 FL：训练核心接受混合栈，Java 把守平台层与推理层

**目标场景**：横向联邦（多机构同特征不同样本，如多家医院联合训练）、纵向联邦（同样本不同特征，如银行 × 电商联合风控模型）。

**生态现实**：联邦学习训练框架深度绑定 PyTorch/TensorFlow，核心生态被 Python 垄断。强行用 Java 重写训练框架（如基于 DL4J 自研）工作量与风险均不可控，**不建议**。

**候选方案与 Java 边界划分**：

| 组件 | 项目 | 语言 | Java 团队的角色 |
|---|---|---|---|
| 联邦训练引擎 | **FATE**（FederatedAI/FATE） | Python | 当黑盒平台部署运维，不做二次开发 |
| 在线联邦推理 | **FATE-Serving** | **纯 Java**（Spring Boot + gRPC） | 直接对接、可深度二次开发，业务系统的主要集成点 |
| 任务调度/管理面 | 自研 | Java | 统一的任务编排、审计、多路线入口 |
| 端侧联邦（可选） | Flower Android SDK | Kotlin/Java | 移动端场景可用 Java 写客户端 |

**可行性论证**：

- FATE 是国内金融行业事实标准，通过信通院评测，合规背书充分；其推理侧 FATE-Serving 本身就是 Java 工程，与业务系统（Java）同栈集成顺畅。
- 混合栈的代价集中在**部署运维**（Python 环境、容器化）与**平台升级**（FATE 版本演进），通过容器化部署（K8s + 官方镜像）与版本锁定可控。
- 纵向联邦中的加密样本对齐（PSI）与梯度加密（Paillier），恰好可复用本方案 2.1/2.2 的 Java 能力，形成协同。

**结论：可行，但需接受"训练 Python、平台与推理 Java"的混合栈边界，这是生态现实下的最优解而非妥协。**

### 2.4 DP：Java 最友好的一条路线

**目标场景**：统计结果对外发布/开放前的脱敏（防差分攻击、防个体反推）；联邦学习输出模型的隐私加固。

**候选方案**：

| 项目 | 语言 | 评估 |
|---|---|---|
| **Google differential-privacy** | **官方 Java 实现**（另有 C++/Go） | 提供带噪 count/sum/mean/percentile 等聚合原语，含隐私预算管理，工程质量高，**首选** |
| OpenDP / SmartNoise | Rust/Python | 仅作方法论参考 |

**可行性论证**：

- 作为普通 Maven 依赖引入即可，无跨语言、无重型基础设施，是四条路线中集成成本最低的。
- 工程要点不在库本身，而在**隐私预算（ε）的治理**：需要平台层统一记账（每个数据集的累计消耗）、超预算熔断与审计留痕——这正是 Java 平台层的职责。

**结论：完全可行，Java 原生，一期即可全量交付。**

## 3. 总体设计

### 3.1 设计原则

1. **统一平台，路线插件化**：四条路线以能力插件形式挂接到统一的任务调度与治理平台之下，对业务方暴露统一 API，屏蔽底层协议差异；
2. **Java 边界清晰**：平台层（调度/网关/审计/预算治理）、MPC/PHE/DP 计算引擎、FL 推理层为 Java；FL 训练引擎（Python）与 FHE 引擎（C++）作为受管的外部执行单元；
3. **节点对等部署**：每个参与方部署一个对等的"隐私计算节点"，节点间通过 mTLS 加密通道通信，不存在拿到明文的中心方；
4. **默认安全**：所有跨方通信走密态（秘密分享/密文/梯度），所有出库结果过 DP 网关，所有操作落审计日志。

### 3.3 模块设计要点

**（1）统一 API 网关与任务模型（Java）**

- 业务方提交的是**任务**（如"与 B 方做 PSI 求交""发布加噪统计报表"），不感知底层协议；
- 任务模型统一为 DAG：`数据准备 → 样本对齐(PSI) → 计算/训练 → 结果保护(DP) → 出库`，各环节绑定到对应引擎；
- 技术栈：Spring Boot 3.x + gRPC（跨方通信）/ REST（业务侧），任务状态持久化用 PostgreSQL/MySQL。

**（2）MPC 引擎（Java 原生）**

- 封装 mpc4j 的 PSI/PIR/联合统计能力为无状态计算算子，FRESCO 补位通用电路场景；
- 平台层负责会话生命周期（协商、心跳、断点续传）、mpc4j 只负责协议本身；
- 版本锁定 + 协议兼容性回归测试集，对冲研究型库 API 变动风险。

**（3）PHE 引擎（Java 原生）**

- javallier Paillier 为核心，提供密钥生命周期管理（生成/轮换/销毁，密钥入 KMS 或 HSM）；
- 提供密文打包与批处理优化；同时作为 FL 纵向场景的梯度加密组件被复用。

**（4）DP 引擎与隐私预算中心（Java 原生）**

- Google DP Java 库提供加噪原语；
- **隐私预算中心为平台级横切模块**：按数据集记账 ε 消耗，超限熔断，全量审计——所有对外出库结果强制过 DP 网关（预算可配置为 0 噪声以支持白名单场景，但必须显式声明并留痕）。

**（5）FL 适配器（Java ↔ 混合栈边界）**

- FATE 以官方容器镜像部署（K8s），Java 适配器通过 FATE Flow 的 REST API 提交与监控训练任务，不侵入 FATE 内部；
- 在线推理直接集成 FATE-Serving（Java），与业务系统同栈；
- 纵向联邦的样本对齐调用本平台 MPC 引擎（PSI），梯度保护复用 PHE 引擎，形成能力闭环。

**（6）FHE Sidecar（二期，可选）**

- SEAL/OpenFHE 包成独立 C++ gRPC 服务，与 Java 主进程物理隔离；
- 只有当出现"密文乘法不可回避"的场景（如密文模型打分）才启用，一期不建设。

### 3.4 安全与合规设计

- **通信安全**：跨方一律 mTLS + 双向证书校验，证书由联盟 CA 签发；
- **密钥管理**：Paillier/协议密钥托管至 KMS（如 Vault/云 KMS），支持轮换与销毁审计；
- **最小披露**：协议输出粒度在任务定义时声明（如 PSI 只输出交集基数而非交集明细），网关强制校验；
- **审计**：任务级全链路日志（谁、何时、用哪些数据、跑什么协议、输出了什么、消耗多少预算），满足《个人信息保护法》《数据安全法》下的可追溯要求；
- **对标标准**：产品能力对标信通院"可信隐私计算"评测项，为后续送测预留接口。

### 3.5 性能与容量预估（设计目标）

| 场景 | 规模 | 目标 | 依据 |
|---|---|---|---|
| PSI 求交 | 千万级 ID / 双方 | 专线环境分钟级 | mpc4j 公开基准 + 网络为主要瓶颈 |
| Paillier 密文聚合 | 百万级密文求和 | 单节点分钟级（批处理+并行） | BigInteger 模幂性能 + packing 优化 |
| DP 加噪 | 任意统计结果 | 毫秒级，可忽略 | 纯本地计算 |
| 纵向联邦训练 | 十万~百万样本 | 小时级（FATE 基准为准） | 由 FATE 引擎决定，非 Java 边界内 |

> 注：以上为设计目标而非承诺指标，一期需以 PoC 实测数据修正。

## 4. 风险清单与对策

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| 1 | mpc4j 为研究型库，API 稳定性不确定 | 中 | 版本锁定；协议层薄封装隔离；建立回归测试集；备选 FRESCO |
| 2 | javallier 社区维护趋缓 | 低 | Paillier 协议简单，保留基于 BigInteger 的自研备份路径 |
| 3 | FHE 无 Java 生产实现 | 高（若一期承诺） | 一期范围明确排除 FHE；二期以 sidecar 引入，不污染主链路 |
| 4 | FATE 混合栈运维复杂度 | 中 | 容器化 + 版本锁定；只经 REST API 集成，不改 FATE 内部 |
| 5 | MPC/PHE 性能不达预期 | 中 | 立项前先做 PoC 基准测试（见 §5 里程碑 M1），以实测定 SLA |
| 6 | 隐私预算治理形同虚设 | 中 | DP 网关平台级强制，出库唯一通道，预算例外需审批留痕 |
| 7 | 多方异构环境交付摩擦 | 低 | JVM 跨平台优势 + 全组件容器化交付 |

## 5. 实施路线（建议里程碑）

| 里程碑 | 内容 | 交付物 |
|---|---|---|
| **M1：PoC（4~6 周）** | mpc4j 双方 PSI 打通；javallier 密文求和；Google DP 加噪出库；实测性能基准 | 可运行 demo + 基准报告，验证 §3.5 假设 |
| **M2：平台一期（3 个月）** | 统一网关/调度/审计/预算中心 + MPC/PHE/DP 三引擎生产化 | 支持联合统计与 PSI 的可交付平台 |
| **M3：联邦集成（2 个月）** | FATE 容器化部署 + Java 适配器 + FATE-Serving 推理集成 | 纵向联邦风控建模端到端跑通 |
| **M4：增强期（按需）** | FHE sidecar、PIR 隐匿查询、信通院送测 | 可选增强能力 |

---

## 6. 结论

1. **四条路线在 Java 技术栈下均可行**，且 MPC、半同态 HE、DP 三条可做到 **Java 原生实现、无妥协交付**；
2. 两处需要接受的现实边界：**FL 训练核心用 FATE（Python，黑盒化部署）**、**全同态 HE 用 C++ sidecar（且延后到二期）**——两者都有清晰的隔离手段，不影响平台主体的 Java 纯度与可维护性；
3. 建议按 §5 路线先做 PoC 验证性能假设，再启动平台一期建设。
