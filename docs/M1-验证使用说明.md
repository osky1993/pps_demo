## 1. 你将验证什么

M1 用四个可运行的 PoC 论证「MPC / HE / DP 三条隐私计算路线在 Java 技术栈下可行」：

| 验证项 | 内容 | 对应结论 |
|---|---|---|
| 验证一 PSI | 两方隐私求交（mpc4j：RR22 / KKRT16），S/M/L 三档规模 | H1：千万级分钟级 ✅ |
| 验证二 PHE | Paillier 密文聚合（javallier），分阶段吞吐 | H2：百万级临界达标 ⚠️ |
| 验证三 DP | 差分隐私加噪出库（Google DP），误差矩阵 + 预算熔断 | H3：误差可控 ✅ |
| 验证四 E2E | 银行×电商联合统计端到端链路 + 审计 | H4：链路闭环 ✅ |

**先读边界声明**：

- M1 全部实测在**单机 loopback**（单进程内存 RPC）完成，结论为排除网络因素的计算上限；
  真实双机 + 网络矩阵是 M2 立项前的遗留项，本文 §4 给出双机环境的预备规范与当前能做/不能做的清单；
- 验证数据由固定种子生成器构造（无需任何外部数据），交集是构造出的已知真值，
  因此所有正确性验证都是与真值的**全量比对**，不是抽样。

## 2. 获取源码与编译

### 2.1 前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| JDK | **必须 17.x**（不能用 18+） | mpc4j 以 `release 17 + --enable-preview` 编译，preview 产物要求编译与运行的 JDK 特性版本完全一致；用 21 构建会直接报「源发行版 17 与 --enable-preview 一起使用时无效」 |
| Maven | 3.9+ | |
| Git | 任意近期版本 | |
| 内存 | 16 GB 起；跑 L 档 PSI 需 **32 GB** | L 档 KKRT16 需 `-Xmx26g` |
| GMP（可选） | libgmp 6.x | 仅影响 PHE 盲化速度（×1.5），不装不影响功能与结论复现 |

macOS 选择 JDK 17：`export JAVA_HOME=$(/usr/libexec/java_home -v 17)`；
Linux 用 `update-alternatives` 或 SDKMAN 切换。以下命令均假设 `JAVA_HOME` 已指向 JDK 17。

### 2.2 获取与编译（首次约 5 分钟）

```bash
# 1. 获取本工程源码（mpc4j v1.1.5 已登记为 submodule，务必带 --recurse-submodules；
#    路径按实际仓库地址替换。已 clone 未拉子模块的话补一句：git submodule update --init）
git clone --recurse-submodules <本仓库地址> ppc_demo && cd ppc_demo
```

```bash
# 2. 构建 mpc4j（未发布 Maven Central，需源码 install 到本地仓库，仅首次）
mvn -f third_party/mpc4j/pom.xml install -DskipTests -Dmaven.javadoc.skip=true -pl mpc4j-s2pc-pso -am
```

```bash
# 3. 构建本工程并运行全部单元测试（15 个，预期全绿）
mvn verify
```

```bash
# 4. 生成各模块运行 classpath（后续验证命令引用 target/cp.txt）
mvn -q install -DskipTests
mvn -q dependency:build-classpath -Dmdep.outputFile=target/cp.txt
```

**编译成功标志**：`mvn verify` 输出 `BUILD SUCCESS` 且 7 个模块全部 SUCCESS、
15 个测试 0 失败。任何一步报错先查 §7 常见问题。

## 3. 验证数据准备

**无需准备任何外部数据。** 所有数据由 `ppc-common` 的生成器按固定种子构造：

- **ID 集合**（`IdSetGenerator`）：64 位随机 ID，先构造指定规模的交集，再补两方差集并洗牌——
  交集就是已知真值，协议输出与它全量比对；
- **金额列**（`ValueGenerator`）：对数正态分布（中位数约 30 元，贴近真实消费形态），
  以「分」为单位的整数（Paillier 整数编码规范），按 clamp 上界截断。

数据参数统一在工程根目录 [poc.yaml](../poc.yaml) 配置：

| 参数 | 含义 | 可选值 |
|---|---|---|
| `dataset.profile` | 数据档位 | `S`（1万）/ `M`（100万）/ `L`（1000万） |
| `dataset.seed` | 随机种子 | 任意 long；**相同种子 → 完全相同的数据**，跨机器可复现 |
| `dataset.intersectionRatio` | 交集比例 | 0~1，基准口径：S=0.5，M=0.3，L=0.1 |
| `psi.protocol` | PSI 协议 | `rr22` / `kkrt16` |
| `phe.keyBits` | Paillier 密钥位长 | 2048（基线）/ 3072 |
| `dp.epsilon` / `dp.clampUpper` / `dp.budgetTotal` | DP 参数 | 基线 1.0 / 100000 / 10.0 |

复现基准报告的 M / L 档配置，只需复制 poc.yaml 改两行：

```bash
sed 's/profile: S/profile: M/; s/intersectionRatio: 0.50/intersectionRatio: 0.30/' poc.yaml > poc-M.yaml
sed 's/profile: S/profile: L/; s/intersectionRatio: 0.50/intersectionRatio: 0.10/' poc.yaml > poc-L.yaml
```

## 4. 验证环境搭建

### 4.1 单机环境（M1 结论的全部验证在此完成）

一台满足 §2.1 要求的机器即可。要点：

- PSI / E2E 运行必须带 JVM 参数 `--enable-preview --add-modules jdk.incubator.vector`
  （mpc4j preview 约束，漏了会报 preview 类加载错误）；
- 各档位建议堆内存：S/M 档 `-Xmx8g`；L 档 KKRT16 **`-Xmx26g`**（12g 实测 OOM）；
- 基准数据统一落 `bench-result.csv`（首行表头，可直接进表格工具比对）。

### 4.2 多机（双机）环境：预备规范与现状边界

**现状（务必了解）**：M1 代码的 PSI 入口是 `LocalPsiRunner`（单进程内存 RPC），
**尚未提供双机 netty 入口**——双机 PSI 验证属遗留项 1，计划在 M2 立项前补齐
（mpc4j 自带 `NettyRpcManager`，改造点仅限 `LocalPsiRunner` 的 RPC 构造处，协议代码不变）。

当前双机环境下**可以做的**：在两台机器上分别独立跑完 §5 的全部验证（交叉复现结论）；
用相同 seed 在两台机器生成数据，校验生成器跨机器一致性（`md5` 比对导出的 ID 文件）。
**不能做的**：跨机 PSI 协议交互、真实网络下的 PSI 通信量/耗时测量。

为遗留项 1 预备的双机规范（届时直接可用）：

| 项 | 规范 |
|---|---|
| 机器 | 2 台同构机器（参考基线：10 核 / 32 GB），角色 server / client |
| 网络 | 千兆交换机直连（LAN 场景）；防火墙放行 `party.local` 端口（默认 9001/9002） |
| 配置 | 双方 poc.yaml 的 `party.role` 分别为 server/client，`peer` 指向对方 IP:端口；`dataset.seed` 必须一致 |
| WAN 模拟 | Linux 侧 `tc qdisc add dev <网卡> root netem delay 20ms rate 50mbit`，测完 `tc qdisc del` 还原 |
| 网络基线 | 正式测量前先记录 `iperf3` 带宽与 `ping` RTT，写入报告环境指纹 |

## 5. 开展验证工作

以下命令均在工程根目录执行，`$JAVA_HOME` 指向 JDK 17。
每步都给出**预期结果**（参考值来自 [基准测试报告](./M1-基准测试报告.md)，Apple M4 / 32GB；
不同硬件允许数倍波动，**量级一致 + 校验通过**即视为复现成功）。

### 步骤 0：回归测试基线

```bash
mvn verify
```

预期：15 个测试全绿。这一步已覆盖全部功能正确性（PSI 双协议真值比对、
Paillier 密态聚合一致性、DP 预算熔断语义、E2E 全链路）。后续步骤是性能与行为的人工复核。

### 验证一：PSI 隐私求交（H1）

```bash
# S 档冒烟（秒级）
$JAVA_HOME/bin/java --enable-preview --add-modules jdk.incubator.vector -Xmx4g \
  -cp "ppc-psi/target/classes:ppc-common/target/classes:$(cat ppc-psi/target/cp.txt)" \
  com.ppcdemo.psi.PsiBenchMain poc.yaml rr22
```

```bash
# M 档双协议（预期：rr22 约 10s/50MB，kkrt16 约 17s/150MB）
$JAVA_HOME/bin/java --enable-preview --add-modules jdk.incubator.vector -Xmx8g \
  -cp "ppc-psi/target/classes:ppc-common/target/classes:$(cat ppc-psi/target/cp.txt)" \
  com.ppcdemo.psi.PsiBenchMain poc-M.yaml rr22
```

```bash
# L 档（需 32GB 内存机器；预期约 3 分钟 / 1.36GB 通信）
$JAVA_HOME/bin/java --enable-preview --add-modules jdk.incubator.vector -Xmx26g \
  -cp "ppc-psi/target/classes:ppc-common/target/classes:$(cat ppc-psi/target/cp.txt)" \
  com.ppcdemo.psi.PsiBenchMain poc-L.yaml kkrt16
```

检查点：每次输出末行必须含「校验通过」（交集与构造真值全量一致）。
**预期失败项**（这是结论的一部分，不是 bug）：`poc-L.yaml` + `rr22` 会抛
`num (...) must be in range (0, 4194304]`——RR22 底层 VOLE 的 2^22 单批上限，见基准报告 §2.2。

### 验证二：Paillier 密文聚合（H2）

```bash
# 10 万条分阶段吞吐（纯 Java 预期：encrypt 毫秒级，obfuscate ~160s——这就是 H2 的瓶颈实证）
$JAVA_HOME/bin/java \
  -cp "ppc-phe/target/classes:ppc-common/target/classes:$(cat ppc-phe/target/cp.txt)" \
  com.ppcdemo.phe.PheBenchMain poc.yaml 100000
```

```bash
# （可选）GMP 加速对比：先安装 libgmp（macOS: brew install gmp / Debian: apt install libgmp10）
$JAVA_HOME/bin/java -Djna.library.path=/opt/homebrew/lib \
  -cp "ppc-phe/target/classes:ppc-common/target/classes:$(cat ppc-phe/target/cp.txt)" \
  com.ppcdemo.phe.PheBenchMain poc.yaml 10000
```

检查点：输出「校验通过：Σ=…」（密态求和与明文一致）；obfuscate 吞吐落在数百条/秒量级，
encrypt 在百万条/秒量级——两者的巨大差距正是报告 §3 的核心发现。
GMP 生效的标志：不再出现「Gmp library is not available」告警（Linux 的 jna.library.path
按实际 libgmp 位置调整，如 `/usr/lib/x86_64-linux-gnu`）。

### 验证三：DP 加噪出库（H3）

```bash
$JAVA_HOME/bin/java \
  -cp "ppc-dp/target/classes:ppc-common/target/classes:$(cat ppc-dp/target/cp.txt)" \
  com.ppcdemo.dp.DpDemoMain poc.yaml
```

检查点（约 10 秒出全表）：

- 误差矩阵随 ε 增大单调收窄；ε=1.0 时 sum(n=100万) 的 P99 在 0.01% 量级
  （噪声随机，具体数字每次不同，量级稳定）；
- 末尾预算演示：「成功出库 10 次后熔断」+ 剩余 ε=0.0 的异常信息（budgetTotal=10、单次 ε=1）。

### 验证四：端到端链路（H4）

```bash
$JAVA_HOME/bin/java --enable-preview --add-modules jdk.incubator.vector -Xmx8g \
  -cp "ppc-e2e/target/classes:ppc-psi/target/classes:ppc-phe/target/classes:ppc-dp/target/classes:ppc-common/target/classes:$(cat ppc-e2e/target/cp.txt)" \
  com.ppcdemo.e2e.E2eDemoMain poc-M.yaml
```

检查点（约 15 秒，五步叙事输出）：

1. 每步标注了「谁在此刻看得见什么」——这是给合规方看的披露控制叙事；
2. 步骤 3 密态聚合 30 万条应在**秒级**（验证「仅盲化最终Σ」的设计使验证二的瓶颈消失）；
3. 步骤 5 出库偏差在 0.001% 量级、预算剩余 ε=9.0；
4. 末行「密态聚合与明文对照一致 ✓」+ 审计 JSON 路径（打开确认字段：任务/协议/交集规模/ε 消耗/分阶段耗时）。

## 7. 常见问题（FAQ）

**Q1：构建报「源发行版 17 与 --enable-preview 一起使用时无效（仅发行版 21 支持预览语言功能）」**
用了 JDK 21+ 构建。切回 JDK 17（§2.1），ppc-psi 的 enforcer 也会拦截并提示。

**Q2：运行报 `Preview features are not enabled` 或 preview 类加载错误**
漏了 JVM 参数。PSI / E2E 相关命令必须带 `--enable-preview --add-modules jdk.incubator.vector`。

**Q3：运行报 `UnsatisfiedLinkError: no mpc4j-native-tool in java.library.path`**
不应出现——本工程已在 `LocalPsiRunner` 中固定 `EnvType.STANDARD_JDK`（纯 Java 路径）。
若你改动了 config 构造，恢复 `config.setEnvType(EnvType.STANDARD_JDK)` 即可；
编译 mpc4j 的 C++ native-tool 属可选加速，不在 M1 范围。

**Q4：L 档 PSI 抛 `OutOfMemoryError`**
KKRT16 千万级需 `-Xmx26g`（32GB 内存机器）。内存不足就只验证 M 档——
L 档结论可引用基准报告，或换大内存机器复测。

**Q5：PHE 出现 JNA/Gmp 相关告警甚至栈**
仅意味着 GMP 原生加速不可用、回退纯 Java——**功能与校验不受影响**。
需要加速对比时按验证二的可选步骤安装 libgmp 并设置 `-Djna.library.path`。

**Q6：`third_party/mpc4j` 构建失败**
先确认 JDK 17（Q1 同因最常见）。仍失败时检查 Maven 能否访问外网仓库（mpc4j 依赖较多）；
公司内网环境配置好私服 mirror 再重试。

**Q7：两台机器生成的数据不一致？**
检查双方 `dataset.seed` 与 `profile` 是否完全一致——生成器是确定性的，相同参数必然逐字节一致。

**Q8：我的性能数据与报告差很多**
报告环境是 Apple M4 笔记本（10 核 / 32GB / 纯 Java 路径 / loopback）。不同 CPU、核数、
是否被其他负载抢占都会造成数倍差异；判据以 §6 的「量级 + 校验」为准，不比对绝对值。
