## 1. M1 的定位与目标

### 1.1 定位

M1 是**技术验证（PoC）**，不是产品开发。它要回答的是总体设计中悬而未决的三个假设性问题，为 M2 平台一期的立项提供实测依据：

| # | 待验证假设（来自总体设计 §3.5） | 验证方式 |
|---|---|---|
| H1 | mpc4j 千万级 PSI 在专线/局域网环境可达分钟级 | PoC-1 基准测试 |
| H2 | javallier 百万级 Paillier 密文求和单节点分钟级 | PoC-2 基准测试 |
| H3 | Google DP Java 库可满足加噪出库需求，误差可控 | PoC-3 功能与误差验证 |
| H4 | 三者可以串成"求交 → 密文聚合 → 加噪出库"的端到端链路 | PoC-4 集成演示 |

### 1.2 目标（验收标准，Exit Criteria）

M1 结束时必须交付：

1. **可运行的 demo 工程**：Maven 多模块，一条命令可分别启动四个 PoC；
2. **基准测试报告**：三种网络环境（本机回环 / 千兆局域网 / 模拟广域网）下的实测数据，直接回答 H1/H2 是否成立；
3. **技术评估结论**：mpc4j / javallier / Google DP 三个库的工程化风险清单（API 质量、构建难度、文档缺口），给 M2 的"用/不用/怎么包"结论；
4. **Go / No-Go 建议**：若实测与假设偏差超过 5 倍，给出替代路径分析（换协议、换库或调整 SLA）。

### 1.3 明确不做（Out of Scope)

- 不做统一网关、调度器、审计中心（M2 范围）；
- 不做 FATE / 联邦学习相关内容（M3 范围）；
- 不做 FHE（M4 范围）；
- 不做生产级密钥管理（PoC 密钥落本地文件即可，但代码留出 KMS 接口位）；
- 不做 UI，全部命令行驱动。

### 2.1 工程骨架（Maven 多模块）

```

├── pom.xml                        # parent：统一依赖版本、JDK 17、编译插件
├── docs/                          # 设计文档（本文件所在）
├── ppc-common/                    # 公共模块：数据生成器、计时器、报告输出、配置加载
├── ppc-psi/                       # PoC-1：mpc4j 两方 PSI
├── ppc-phe/                       # PoC-2：javallier Paillier 密文聚合
├── ppc-dp/                        # PoC-3：Google DP 加噪出库
├── ppc-e2e/                       # PoC-4：端到端集成（依赖上面三个模块）
└── ppc-bench/                     # 基准测试驱动（JMH + 自研网络场景脚本）
```

**技术基线**：

| 项 | 选择 | 说明 |
|---|---|---|
| JDK | 17 LTS | mpc4j 要求 17+；Paillier 的 BigInteger 在 17 上有性能改进 |
| 构建 | Maven 3.9+ | 与 mpc4j 自身构建体系一致 |
| 日志 | SLF4J + Logback | 统一格式，基准数据单独走 CSV 输出通道 |

**（已于 W1 核实，2026-08-01——下表为确证结论，替代 v0.1 的预期）**

| 依赖 | 确证坐标与接入方式 | 实测结论 |
|---|---|---|
| mpc4j | `edu.alibaba:mpc4j-s2pc-pso:1.1.5`，未发布 Central，源码构建：`git clone --branch v1.1.5` → `JAVA_HOME=jdk17 mvn install -DskipTests -pl mpc4j-s2pc-pso -am`（约 31s，10 模块） | ① POM 写死 `--enable-preview` + `jdk.incubator.vector`：**必须 JDK 17 构建，运行也必须 JDK 17 + preview 参数**（javac 21 拒绝 release 17 + preview 组合）；② 默认 `EnvType.STANDARD` 依赖 C++ native-tool（sodium ECC 等），未编译时 `UnsatisfiedLinkError`——**PoC 用 `config.setEnvType(EnvType.STANDARD_JDK)` 纯 Java 路径**，native 加速对比留作 W3 基准项 |

## 3. PoC-1：mpc4j 两方 PSI 详细设计

### 3.1 验证内容

- 功能：两个独立 JVM 进程（可分置两台机器）完成 PSI，输出交集且与真值一致；
- 性能：S/M/L 三档 × 三种网络环境的耗时与通信量矩阵；
- 工程：mpc4j 的会话建立、异常行为（断连、数据倾斜）的表现。

### 3.2 协议选型

mpc4j 的 PSI 实现集中在其 PSO（Private Set Operation）相关模块。选型策略：

| 优先级 | 协议 | 理由 |
|---|---|---|
| 首选 | RR22（Blazing Fast PSI）系 | 近年综合最优：通信量与计算平衡，适合千万级 |
| 对照 | KKRT16 系 | 经典 OT 扩展基线，实现最成熟，用于交叉验证首选协议的结果与性能比 |

> **已核实（v1.1.5 源码）**：统一经 `PsiFactory.createServer/createClient(rpc, otherParty, config)` 创建；
> RR22 = `psi.mpoprf.rr22.Rr22PsiConfig`（Builder 需传 `SecurityModel.SEMI_HONEST`，另有 MALICIOUS 档），
> KKRT16 = `psi.cuckoo.kkrt16.Kkrt16PsiConfig`；元素类型 `Set<ByteBuffer>`（PoC 统一 16 字节 block 编码）；
> 通信量可直接从 `Rpc.getSendByteLength()` 采集。测试用 `MemoryRpcManager`，双机用 netty RpcManager。
> 选型结论要求：**两种协议都跑通，报告中并列数据**，避免单协议实现有坑导致误判整个库。

### 3.3 运行架构

```
┌────────── 机器 1 ──────────┐        ┌────────── 机器 2 ──────────┐
│  PsiServerMain (A 方)      │  gRPC/  │  PsiClientMain (B 方)      │
│  ├─ 加载 A 方 ID 集合       │◄─netty─►│  ├─ 加载 B 方 ID 集合       │
│  ├─ mpc4j Rpc 端点          │  专线/  │  ├─ mpc4j Rpc 端点          │
│  └─ MetricsRecorder        │  netem  │  └─ MetricsRecorder        │
└────────────────────────────┘        └────────────────────────────┘
```

- 通信直接使用 mpc4j 自带的 netty Rpc 层（不自研传输），我们只在外层包一层连接重试与计时；
- 单机模式（两进程走回环）与双机模式（走真实网卡）用同一份代码、不同 `poc.yaml`。

### 3.4 关键实现点

1. **入口**：`ppc-psi` 提供 `PsiPartyMain --role=server|client --dataset=S|M|L --protocol=rr22|kkrt16`；
2. **计时切面**：区分 `setup`（基础 OT、密钥协商）与 `online`（正式求交）两阶段——M2 做 SLA 时这两段的优化空间完全不同；
3. **内存档案**：L 档位跑通所需的 `-Xmx` 下限要实测记录（这决定 M2 的容器规格建议）；
4. **正确性断言**：交集结果与 `IdSetGenerator` 构造的真值全量比对，不抽样。

### 3.5 网络场景

| 场景 | 实现方式 | 模拟目标 |
|---|---|---|
| loopback | 单机双进程 | 排除网络因素的计算上限 |
| LAN | 两台机器，千兆交换机 | 机构内网/同城专线 |
| WAN-sim | `tc qdisc netem` 注入 20ms RTT + 50Mbps 限速 | 跨城专线保守估计 |

WAN-sim 的 netem 脚本放入 `ppc-common/net/`，报告中必须注明注入参数。

## 4. PoC-2：Paillier 密文聚合详细设计

### 4.1 验证内容

- 功能：A 方生成密钥对并把公钥交给 B 方；B 方对 100 万条数值逐条加密、密文累加；A 方解密总和，与明文求和一致；
- 性能：加密吞吐（条/秒）、密文累加吞吐、序列化后的密文体积；
- 工程：javallier 在 JDK 17 下的兼容性结论。

### 4.2 运行架构与关键实现点

单模块内完成（聚合场景的网络传输不是瓶颈，PoC 阶段不拆双机）：

```
PheBenchMain
 ├─ 1. KeyGen(2048bit)             # 记录耗时；密钥序列化落本地文件（留 KMS 接口位）
 ├─ 2. encrypt × N（并行流分片）     # 核心基准：单线程 vs. 并行(核数) 两组数据
 ├─ 3. ciphertext add × N          # 密文累加（纯模乘，预期远快于加密）
 ├─ 4. decrypt(sum)                # 一次
 └─ 5. assert sum == 明文Σ          # BigDecimal 精度处理：金额×100 转整数入密文
```

1. **编码约定**：Paillier 只对整数运算，金额统一放大 100 倍转 long 编码，解密后还原——该约定要写进 `ppc-common` 作为平台级编码规范的雏形；
2. **并行策略**：加密无状态，按分片并行即可；报告给出"单核吞吐 × 核数"与实测并行吞吐的对比（验证无锁竞争）；
3. **密钥位长**：2048 为基线，附 3072 一组数据（合规趋严时的成本预估）；
4. **密文体积**：序列化后单密文字节数 × 百万级 = 跨方传输量，报告需给出，供 M2 估算带宽。

### 4.3 备份方案：自研 Paillier（仅在 javallier 不可用时启动）

触发条件：javallier 与 JDK 17 不兼容且无 patch 余地。
方案：`ppc-phe` 内 `fallback` 包实现教科书 Paillier（`BigInteger` 模幂 + 中国剩余定理解密加速），约 300 行，密码学实现须经第二人 review 并与 javallier（在 JDK 8 容器里）交叉验证密文互通性。**默认不启动此路径，避免 PoC 范围膨胀。**

## 5. PoC-3：DP 加噪出库详细设计

### 5.1 验证内容

- 功能：对一组统计结果（count / sum / mean）加拉普拉斯噪声，ε 可配置；
- 误差验证：固定数据集重复加噪 1000 次，实测误差分布是否符合理论界；
- 治理雏形：单数据集的 ε 预算记账演示（内存版）。

### 5.2 设计

```
DpDemoMain
 ├─ 场景数据：M 档数值列 → 真实 count/sum/mean
 ├─ DpAggregator                    # 包装 Google DP 的 Count/BoundedSum/BoundedMean
 │    └─ 关键参数：ε ∈ {0.1, 1.0, 10}，敏感度上下界（clamp 边界）外置到 poc.yaml
 ├─ ErrorProfiler                   # 重复 1000 次：输出 相对误差分位数表(P50/P95/P99) × ε 矩阵
 └─ BudgetLedger（内存版）           # 每次查询扣减 ε，超限抛 BudgetExhaustedException
```

**关键实现点**：

1. **clamp 边界是业务问题**：BoundedSum 必须给定每条记录的贡献上下界，边界给大了噪声大、给小了截断偏差大——PoC 报告要用实验数据把这个权衡讲清楚，这是 M2 平台把"边界设定"做成任务参数时的依据；
2. **ε 语义示例表**：报告附一页"ε=0.1/1/10 时，100 万人的 count 查询误差大约多少"的直观表格，供非密码学背景的业务方与合规方理解；
3. **BudgetLedger 只做演示**：验证 Google DP 的 API 是否便于外层记账（是否暴露每次查询的实际 ε 消耗），为 M2 隐私预算中心探路。

## 6. PoC-4：端到端集成演示设计

### 6.1 业务叙事（演示脚本用）

> A 银行与 B 电商联合统计："双方共同客户在 B 平台的年消费总额"，A 方不能拿到 B 方明细，B 方不能知道 A 方客户名单，最终结果加噪后出库给分析师。

### 6.2 链路设计

```
A 方进程                                    B 方进程
────────                                    ────────
1. PSI (ppc-psi, M档)  ◄──── mpc4j ────►   PSI
   └─ 双方各自得到交集(或交集索引)
2. 生成 Paillier 密钥对
   公钥 ────────────────────────────────►  3. 对交集用户的消费额逐条加密
                                              密文累加为 Σ
   ◄──────────────────── 密文Σ ───────────
4. 解密得到真实总额
5. DP 加噪 (ε=1.0, BudgetLedger 扣减)
6. 输出：加噪总额 + 审计记录(JSON)
```

**实现要点**：

- 传输层：PSI 复用 mpc4j Rpc；公钥/密文传递用一个极简 gRPC 服务（`ppc-e2e` 内定义 proto，约 2 个 RPC），**不做任何平台化封装**；
- 演示产物：一段 5 分钟可讲完的运行脚本 + 控制台输出设计（每一步打印"谁在此刻看得见什么"），这是给管理层和合规方看的核心材料；
- 审计记录 JSON：字段对齐总体设计 §3.4 的审计要求雏形（任务、数据集、协议、ε 消耗、时间戳）。

### 6.3 安全性说明的诚实边界

演示文档中必须明确声明：PoC 链路中"B 方知道交集"这一信息披露是本演示的设定而非平台终态（M2 会支持只输出交集基数/密态索引的模式），避免 PoC 演示被误解为最终安全模型。

## 7. 基准测试方法论（ppc-bench）

### 7.1 度量规范

| 维度 | 指标 | 采集方式 |
|---|---|---|
| 时间 | 各阶段 wall-clock（setup/online 分离） | StopWatchRecorder |
| 通信 | 双向字节数 | mpc4j 统计接口优先，否则 netty 层拦截 |
| 内存 | 峰值 RSS 与 GC 后堆占用 | `-Xlog:gc` + `ps` 采样脚本 |
| CPU | 平均利用率 | `pidstat` 采样 |

### 7.2 实验纪律

- 每组配置跑 **5 次取中位数**，同时报告最大最小值（PSI 类协议波动主要来自网络）；
- JVM 预热：JMH 管微基准；端到端场景丢弃第一次运行；
- 所有结果落 `bench-result.csv`，报告图表由脚本从 CSV 生成，**禁止手抄数据**；
- 记录完整环境指纹：CPU 型号、核数、内存、JDK 小版本、mpc4j commit hash、网络实测带宽/RTT（iperf3 + ping 基线）。

### 7.3 报告模板（交付物之一）

`docs/M1-基准测试报告.md`，结构：环境指纹 → H1 结果矩阵（协议×规模×网络）→ H2 结果 → H3 误差矩阵 → 与假设的偏差分析 → Go/No-Go 建议。

### 实测数据（Apple Silicon 笔记本 / JDK 17 / loopback / 纯 Java EnvType）

**PSI（H1）——远超假设，提前判定成立：**

| 协议 | 规模 | 耗时 | 通信量 |
|---|---|---|---|
| RR22 | M 档 100万×100万 | **9.5 s** | 50 MB |
| KKRT16 | M 档 100万×100万 | 16.5 s | 150 MB |

RR22 时间与通信量全面占优（与文献一致），确认首选。L 档（千万级）线性外推 <2 分钟，
真实网络下通信量将成主导，待 W3/W4 LAN/WAN-sim 实测。

**PHE（H2）——临界，须带优化路径解读：**

| 阶段（n=10万, 2048bit, 8并行） | 耗时 | 吞吐 |
|---|---|---|
| encrypt（未盲化 g^m 快速路径） | 41 ms | ~240 万条/秒 |
| **obfuscate（盲化 r^n mod n²）** | **160 s（纯Java）/ ~106 s（GMP）** | **626 → 945 条/秒** |
| 密文累加 | 2.4 s | ~4.2 万条/秒 |
| 单密文体积 | 512 B（100 万条 ≈ 488 MB 传输量） | — |

结论：瓶颈在盲化模幂，百万条外推 18~27 分钟，字面上超出「分钟级」。三条已验证/明确的缓解路径：
① GMP 加速已打通（JNA 升 5.14 + `-Djna.library.path=/opt/homebrew/lib`，javallier 走常数时间安全模幂故仅 1.5×）；
② **盲化因子离线预计算**（r^n 与消息无关，可空闲期预生成，在线只剩一次模乘 → 4 万条/秒级）——建议 M2 采纳；
③ 服务器核数线性扩展。H2 判定：**功能成立，性能临界达标，优化路径明确，不构成 Go/No-Go 障碍**。

**DP（H3）——成立，误差远小于直觉预期：**

| ε | count(n=100万) P99 | sum(n=100万) P99 | mean(n=10万) P99 |
|---|---|---|---|
| 0.1 | 0.0046% | 0.0755% | 0.7746% |
| 1.0 | 0.0005% | 0.0078% | 0.0837% |
| 10 | ~0% | 0.0008% | 0.0101% |

百万级聚合下 ε=1.0 的误差对业务完全无感；预算熔断语义验证通过（budgetTotal=10、单次 ε=1.0，第 11 次拒绝且不扣减）。
剖析方法论注记：count/sum 为「确定性聚合+拉普拉斯噪声」，聚合一次、重复采样噪声 1000 次；
mean 误差结构为商式，用真实 BoundedMean 小样本（10万×100 次）实测。

## W4 实施纪要（2026-08-01，续）

### H1 收官：L 档（1000万×1000万）实测

| 协议 | 结果 | 说明 |
|---|---|---|
| KKRT16 | **169.8 s（2.8 分钟）**，通信 1.36 GB，100 万条交集校验通过 | 需 `-Xmx26g`（12GB 堆 OOM，R3 应验后按 Plan 加堆解决） |
| RR22 | 单批不可行 | 底层 WYKW21 VOLE 上限 2^22=4,194,304，经 OKVS 膨胀（约 1.35×）后**单批输入上限约 300 万条**，千万级需分批求交（每批交集规模泄露需在安全声明中注明） |

**H1 判定：成立**（笔记本 + 纯 Java + loopback 2.8 分钟；服务器 + native 加速 + 真实网络下的余量充足）。
两条对 M2 的硬约束记录：① 协议选型随规模切换——百万级以内 RR22 最优，千万级 KKRT16 或 RR22 分批；
② KKRT16 千万级内存档案：26GB 堆（决定容器规格基线）。

### H4 收官：端到端演示（M 档全链路）

`E2eDemoMain` 实测（任务 d0e60fda）：

| 阶段 | 耗时 | 关键披露控制 |
|---|---|---|
| PSI 求交（RR22, 100万×100万） | 22.1 s* | 双方仅见交集（演示设定，§6.3 边界声明） |
| 公钥分发 | <1 ms | 公钥经字节边界传输 |
| B 方密态聚合 30 万条 | **1.5 s** | 单条明细密文不出域，仅盲化最终Σ |
| A 方解密 + DP 出库 | <100 ms | 真值不出库，加噪偏差 0.0008%，预算扣减 ε=1.0 |

*与独立基准 9.5s 的差异来自并行的 L 档后台任务抢占 CPU。

**关键设计发现**：B 方本地密态聚合场景中只需盲化最终Σ一次，
W2 发现的逐条盲化瓶颈（945 条/秒）在此链路整体消失——30 万条聚合仅 1.5 秒。
该结论应写入 M2 的 PHE 引擎设计：**盲化时机跟随数据出域边界，而非默认逐条盲化**。

**H4 判定：成立**。跨方数据全部经 `Transport` 字节边界传递（序列化已证明），
换 gRPC/netty 仅替换传输实现；审计 JSON（字段对齐总体设计 §3.4）随任务落盘。
