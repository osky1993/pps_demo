## 1. M3 的定位与目标

### 1.1 定位

M2 平台已交付「联合统计」类任务的治理闭环；M3 把**联合建模**（纵向联邦学习）纳入同一个
治理框架：**训练引擎用 FATE（Python，黑盒化部署），Java 平台把守协商、审计、预算与模型出库；
在线推理用 FATE-Serving（纯 Java）与业务系统同栈集成。**

一句话目标：**银行 A × 电商 B 的纵向联邦风控模型，从契约协商到模型出库到在线打分，
端到端跑通且全程可治理。**

### 1.2 验收标准（Exit Criteria）

1. **纵向联邦训练端到端**：A（有标签方）× B（特征方）经平台契约协商后，
   在各自 FATE 集群上完成样本对齐 + 纵向逻辑回归（或 SecureBoost）训练，
   训练指标（AUC/KS）落平台审计；
2. **模型出库治理**：模型导出视同出库物——须经模型出库审批（对齐 ε=0 例外审批语义），
   模型文件指纹与评估指标入审计链；未审批的模型无法离开节点；
3. **在线推理**：FATE-Serving 部署并加载已审批模型，Java 业务侧完成单笔评分调用
   （双方在线特征联合推理），P99 延迟实测记录；
4. **平台治理复用**：联邦任务走 M2 的契约/状态机/审计/白名单审批，任务全生命周期可查；
5. 交付物：可部署制品（FATE + 平台的 compose 编排）、《M3 部署运维手册》、
   《M3 验收报告》、验收演示脚本。

### 1.3 明确不做（Out of Scope）

- 横向联邦（架构预留 taskType，实现只做纵向两方）；
- 三方及以上、带仲裁方（arbiter）拓扑之外的复杂拓扑；
- 自研联邦算法或改造 FATE 内核（FATE 是黑盒，只经官方 API 集成）；
- 联邦特征工程平台化（一期特征列在契约中静态声明）;
- DP-SGD 训练（FATE 能力允许时作为可选参数透传，不承诺；模型泄露的 ε 语义研究留 M4）；
- GPU 训练与大规模性能调优。

### 1.4 M2/M2.5 资产承接表

| M2 资产 | M3 用法 |
|---|---|
| TaskContract / 状态机 / NegotiationService | 新增 taskType=FEDERATED_TRAINING / FEDERATED_INFERENCE，协商流程原样复用 |
| 审计中心（哈希链） | 训练事件流（提交/对齐/迭代里程碑/评估/导出）映射为审计事件 |
| ExceptionApprovalService | 升格为通用「出库审批」：模型导出复用其全员审批语义 |

| psi-engine | 二期换装 FATE 对齐的备选（见 §4.3 决策）；样本量探查（基数）可先行复用 |
| mTLS 证书体系 | FATE 集群间通信（rollsite/osx）证书与平台同源签发 |
| deploy/ compose 体系 | 扩展 FATE 容器编排 |
| 网络矩阵结论（M2.5 #5） | FATE 跨方通信的带宽预估参考（纵向 LR 每轮梯度交换量级评估） |

## 2. 需求分析

### 2.1 业务场景（贯穿全程的验收叙事）

> 银行 A 有贷款客户的标签（是否逾期）与金融特征；电商 B 有共同客户的消费行为特征。
> 双方在数据不出域的前提下联合训练风控评分模型；上线后对新申请人实时联合打分。

### 2.2 角色与用例（在 M2 §2.1 基础上新增）

| 角色 | 新增用例 |
|---|---|
| A 方建模人员 | 发起训练任务（选算法/特征列/超参）、查看训练指标、申请模型出库 |
| B 方审批员 | 审批训练契约（本方特征列白名单）、审批模型出库（联合模型含 B 方贡献） |
| 双方运维 | 部署与监控 FATE 集群、FATE-Serving |
| 业务系统 | 调用在线评分 API |

### 2.3 功能需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| F1 | FEDERATED_TRAINING 任务：契约（算法/特征列/标签方/评估集比例）→ 协商 → FATE 提交 → 状态同步 → 指标落审计 | P0 |
| F2 | FATE Flow 适配器：任务提交/状态轮询/日志摘要/失败原因回传 | P0 |
| F3 | 模型注册表与出库审批：模型指纹、评估指标、审批流、导出包 | P0 |
| F4 | FATE-Serving 集成：模型加载、Java 客户端评分调用 | P0 |
| F5 | 训练数据接入：connector 产出 FATE 可上传的数据集（含指纹复核） | P0 |
| F6 | 推理任务审计：评分调用计数与用途声明（逐笔审计一期不做，按日汇总） | P1 |
| F7 | 特征列级白名单（B 方可声明哪些列可入模） | P1 |
| F8 | 训练任务取消与失败重跑（FATE job kill + 平台状态机对齐） | P1 |

### 2.4 非功能需求

- **资源**：FATE 单方集群开发态 ≥8GB 内存/4 核；单机双集群开发环境 ≥32GB（本机可行）；
- **治理**：训练数据零出域（FATE 保证）+ 平台侧契约/审计背书；模型出库唯一通道；
- **SLA 目标（Sprint 0 实测定稿）**：10万×20特征 纵向 LR 30 轮 ≤ 30 分钟（同宿主双集群）；
  在线单笔评分 P99 ≤ 500ms；
- **可部署**：全组件 compose 一键双方（开发态）；生产拆分手册。

## 3. 版本与部署形态选型（Sprint 0 首要任务）

### 3.1 FATE 版本【S0 已定稿：FATE 1.11.3 + FATE-Serving 2.1.6】

**定稿依据**（详见 [S0 报告](./M3-S0版本PoC报告.md)，2026-08-01）：
FATE-Serving 末版 2.1.7（2023-11，仅配套 1.x 模型格式），2.x 无任何 serving 配套发版痕迹
——双链路判据下熔断规则基于证据提前触发，未消耗试错周期；
1.11.3 standalone 实跑纵向 LR 成功（173s，模型产物验证），serving-server 2.1.6 镜像引导验证通过。
FATE 2.x 升级评估挂 M4（触发条件：官方 serving 配套发布）。

### 3.2 部署形态

```
┌────────────── A 方宿主 ──────────────┐      ┌────────────── B 方宿主 ──────────────┐
│ ppc-node-a（M2 平台，治理面）          │      │ ppc-node-b                            │
│ fate-adapter（本模块，M3）  ──────────┼─REST─┼──▶ 各自只与本方 FATE Flow 交互          │
│ FATE 集群 A（Flow/计算/存储/传输）      │◀────┼─▶ FATE 集群 B（跨方 FATE 传输组件互联） │
│ FATE-Serving A                        │      │ FATE-Serving B                        │
└──────────────────────────────────────┘      └──────────────────────────────────────┘
        治理面：平台 mTLS（既有）                     FATE 传输面：rollsite/osx + 同源证书
```

- **平台不代理 FATE 跨方流量**：FATE 集群间用其原生传输组件直连（证书与平台联盟 CA 同源签发）；
- **fate-adapter 只与本方 FATE Flow 通信**（localhost REST），跨方协调一律走平台契约——
  保持「治理面/数据面」分离的既有原则；
- 开发环境：单机 compose 起双方全套（standalone 版 FATE ×2），资源见 §2.4。

## 4. 关键设计

### 4.1 任务模型扩展

契约新增字段（TaskContract 演进，向后兼容）：

```
taskType = FEDERATED_TRAINING
algorithm         = hetero_lr | hetero_secureboost      # 一期二选一
labelParty        = A                                    # 标签方
featureColumnsA   = [age, income, ...]                   # 各方入模列（B 方审批时校验列白名单 F7）
featureColumnsB   = [consume_30d, ...]
evalRatio         = 0.2
hyperParams       = {maxIter: 30, alpha: 0.01, ...}      # 白名单键透传 FATE
modelReleaseGrain = SCORE_ONLY | MODEL_EXPORT            # 模型出库粒度：仅在线打分 / 允许导出模型包
```

状态机扩展：训练任务的 `RUNNING` 内部细分由 FATE job 状态映射（waiting/running/success/failed/
canceled → 平台 RUNNING/SUCCEEDED-pending-release/FAILED/CANCELLED），映射表进适配器，
平台状态机本身不改（RELEASING 仍是模型出库治理关口）。

### 4.2 FATE Flow 适配器（ppc-platform-fate）

```java
public interface FederationEngine {                    // 平台侧抽象（对齐 EngineRunner 风格）
    String submitTraining(TrainingSpec spec);          // → FATE job_id
    JobStatus poll(String jobId);                      // 状态 + 进度 + 指标快照
    void cancel(String jobId);
    ModelRef exportModel(String jobId, Path target);   // 模型包 + 指纹（仅出库审批通过后可调）
}
```

- 实现 `FateFlowClient`：FATE Flow REST（submit_job / query_job / job_log / model_export），
  DSL/conf 由 `TrainingSpec` 模板化生成（模板随算法枚举固化，杜绝自由 JSON 注入）；
- **轮询与审计**：适配器轮询周期 30s，状态变迁与指标快照（loss 曲线关键点、最终 AUC/KS）
  写审计事件 `FATE_JOB_*`；FATE 日志不整段入审计（体积），仅摘要 + 本地日志路径；
- 失败语义：FATE job failed → 平台任务 FAILED（幂等重跑 = 新 FATE job，同契约）；
- **数据上传**：训练前适配器把 connector 产出的数据（指纹复核后）经 FATE Flow upload 接口
  灌入本方集群，任务结束按契约保留策略清理。

### 4.3 样本对齐决策（显式 ADR）

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. FATE 内置 intersection（一期采用）** | 与训练管线原生衔接、黑盒完整性 | 对齐协议由 FATE 决定（RSA/ECDH PSI），平台仅审计不掌控 |
| B. 平台 psi-engine 对齐 → 结果注入 FATE | 协议自主（RR22/KKRT16/分批）、与统计任务同一引擎 | FATE 外部对齐结果注入路径非标准，工程险高 |

**ADR-M3-1：一期采用 A**，契约记录 FATE 对齐协议类型与交集基数（审计），
并要求对齐前用平台 psi-engine 的 **CARDINALITY_ONLY 预检**（可选开关）给审批方提供
交集规模预估——B 方案作为 M4 备选保留。

### 4.4 模型治理（M3 的治理增量核心）

- **模型注册表**（`model_registry` 表）：taskId、fateJobId、算法、特征列、评估指标(JSON)、
  模型包 SHA-256、状态（TRAINED / RELEASE_APPROVED / EXPORTED / SERVING）；
- **出库审批**：`modelReleaseGrain=MODEL_EXPORT` 时导出须全部参与方审批
  （复用 ExceptionApprovalService，审批对象语义扩展为「出库物」）；
  `SCORE_ONLY` 时模型只允许加载进本联盟的 FATE-Serving，导出接口拒绝；
- **审计**：注册/审批/导出/加载 Serving 各留事件；导出包指纹入链——
  「哪个模型、谁批准、何时出库、部署在哪」全程可追。

### 4.5 在线推理（FATE-Serving 集成）

- FATE-Serving（Java）随 compose 部署，模型经 FATE Flow「model load/bind」进 Serving；
- 平台侧 `ScoringClient`（Java）封装 Serving 的推理接口：入参 = 待评分主体 ID + A 方实时特征，
  B 方特征由 B 侧 Serving 按 ID 从其在线特征源取（一期用离线特征表模拟在线源）；
- 推理延迟基准（P50/P99）入 M3 验收报告；按日调用量汇总入审计（F6）。

### 4.6 预算与合规注记（诚实边界）

联邦训练的隐私泄露度量（梯度泄露、模型反演）**没有与 ε 直接等价的通用记账法**。
一期处理：契约强制声明训练用途与模型出库粒度 + 全程审计；预算中心**不虚构** ε 扣减；
DP-SGD（若 FATE 版本支持）作为可选超参透传并在契约标注。该边界写入验收报告与手册。

## 5. 工程结构增量

```
platform/ppc-platform-fate/        # F1-F5：FederationEngine、FateFlowClient、TrainingSpec 模板、
│                                  #        模型注册表、ScoringClient（依赖 platform-core）
deploy/fate/                       # compose：FATE ×2（standalone）+ FATE-Serving ×2 + 证书接线
docs/M3-*.md                       # 手册与验收报告
```

平台主进程（ppc-platform-server）挂载 fate 模块：管理面新增
`/api/task/fed-training`、`/api/model/{id}`、`/api/model/{id}/approve-release`、
`/api/model/{id}/export`、`/api/score` 端点；CLI 对应扩展。

**JDK 边界**：ppc-platform-fate 纯 Java 17（REST 客户端），无 preview、无 FATE 代码依赖——
FATE 是部署物不是依赖；FATE-Serving 独立进程（其自身 JDK 要求随版本，S0 核实）。

## 9. 结论

M3 的本质是**把黑盒训练引擎纳入白盒治理**：FATE 负责密码学与训练正确性（不重造），
平台负责「谁批准了什么、数据是否被换、模型去了哪」——这正是 M1/M2 建立的治理资产的
自然延伸。最大不确定性集中在 FATE 部署与版本配套（R1/R2），因此 S0 以整整一个 Sprint
做版本 PoC 并设硬熔断；治理增量（模型注册表/出库审批）复用既有组件，工程风险低。
